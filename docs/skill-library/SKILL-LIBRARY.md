## 1. 定义与边界

### 1.1 什么是技能

本工作站中的**技能（Skill）**，是把抽象知识转化为可执行行动的、短小且单一的**实践手册**。

- 一个技能只描述**一种**可复用的工作技法、操作策略或决策程序；
- 技能的目标是**指导当前工作如何做**，而非解释概念本身；
- 技能长度应保持短小，预期技能数量会持续增长；
- 技能必须有能被机器检索的「使用场景提示」与「摘要」。

**例子：**

| 内容 | 归属 |
|---|---|
| “正反馈”是什么、概念来源、理论解释 | 未来的知识库 |
| 在产品交互中加入正反馈的一种具体设计技法 | 技能库 |

### 1.2 技能库与知识库的边界

| 维度 | 知识库（未来开发） | 技能库（本体系） |
|---|---|---|
| 解决的问题 | “这是什么、为什么如此” | “此刻应当怎么做” |
| 内容形态 | 定义、理论、背景、事实、概念关系 | 步骤、判断、技法、检查项、行动约束 |
| 工作时的作用 | 提供理解，不直接指导工作 | 为当前任务提供可执行指导 |
| 组织单元 | 知识条目/概念 | 技能卡片/实践手册 |

知识库不是本期实施范围。技能可在未来通过 `metadata` 链接知识条目，但不应把概念解释膨胀进技能正文。

### 1.3 非目标

本体系当前不把以下能力当作技能库核心：

- 以全文知识库或长篇文档替代实践手册；
- 每轮把所有技能正文或所有技能摘要永久塞进对话上下文；
- 不经用户治理而自动认定一次召回正确；
- 用用户反馈直接、无审查地篡改技能正文；
- 一开始就依赖 embedding、训练模型或外部云服务。

## 2. 基本原则

1. **真源唯一**：技能文件只以 `.agents/skills/` 为真源；管理 UI、蒸馏、索引和检索均直接围绕该目录工作，避免双向同步。
2. **短小、单一、可组合**：一个技能只覆盖一种技法。复杂工作由多个技能在同一轮按需组合，而非用一个巨型技能包办。
3. **场景优先**：技能是否被召回，首先取决于当前工作场景，而不是目录位置或人工浏览顺序。
4. **每轮独立召回**：当前轮的场景决定当前轮的技能；下一轮必须重新检索，不假设上一轮的技能仍适用。
5. **正文按需**：召回阶段只处理技能卡片的结构化信息；正文只在模型决定使用该技能时加载。
6. **引用可见、可纠正**：每次使用技能都应被结构化地声明，使用户可以确认或纠正引用。
7. **反馈影响排序，不直接改知识**：用户反馈首先形成情景记忆并改变未来重排；技能正文的编辑、废弃和归档仍是显式治理行为。
8. **本地优先、可解释**：第一期使用本地 BM25 和明确规则。每次召回能解释“为什么是它”，可由用户检查和修正。

## 3. 真源、目录与文件形态

### 3.1 真源目录

```text
E:\Deepseek Harness\.agents\skills\
  <skill-name>/
    SKILL.md
    references/                 # 可选：按需加载的辅助材料
    assets/                     # 可选：技能专属资源
```

- `skill-name` 必须为 kebab-case；
- `SKILL.md` 是技能卡片主体；
- DSH 文件系统 provider 已扫描该目录（项目级 rank 200）；
- 该目录及其技能内容属于工作站沉淀智能，应进入 git；
- 文件变化会被 DSH watcher 发现，支持会话途中 CRUD。

### 3.2 技能卡片的结构

技能卡片由两部分组成：

1. **YAML frontmatter**：结构化、可检索、可管理的卡片信息；
2. **Markdown 正文**：模型真正加载后遵循的实践手册。

推荐形态：

```yaml
---
name: positive-feedback-micro-reward
description: 在用户完成一个明确操作后，用即时、轻量且可解释的反馈强化继续行动意愿。
whenToUse: 当用户完成目标动作、需要鼓励继续使用或降低下一步行动犹豫时使用；不适合错误提示或高风险操作确认。
triggers:
  - 正反馈
  - 激励用户
  - 完成反馈
  - 强化行为
tags: [product-design, interaction, motivation]
category: product-design
version: 0.1.0
status: active
related: [progress-visibility]
provenance:
  author: human
metadata: {}
---

# 微奖励式正反馈

## 做法

……一种具体技法的步骤、边界与检查项……
```

### 3.3 字段规范

| 字段 | 必填 | 角色 | 说明 |
|---|---:|---|---|
| `name` | 是 | 稳定标识 | kebab-case；目录名与其一致 |
| `description` | 是 | **摘要 / 召回依据** | 用 1–3 句说清“这项技法大致做什么” |
| `whenToUse` | 建议 | **使用场景提示 / 召回依据** | 描述适合场景；应尽量包含不适用边界 |
| `triggers` | 建议 | **使用场景提示 / 硬匹配** | 关键词、别名、用户常用说法、领域术语 |
| `tags` | 建议 | 发现与管理 | 多标签，用于 UI 筛选和辅助重排 |
| `category` | 可选 | 分类 | 一级稳定分类，不替代 tags |
| `version` | 可选 | 生命周期 | 推荐语义版本 |
| `status` | 建议 | 生命周期 | `active` / `draft` / `deprecated` / `archived` |
| `related` | 可选 | 组合与扩展 | 相关技能的 `name` 列表 |
| `provenance` | 可选 | 溯源 | 作者、蒸馏来源、来源会话等 |
| `metadata` | 可选 | 扩展 | 未来知识条目链接、特定领域附加结构等 |
| `disable-model-invocation` | 可选 | DSH 原生启停 | `true` 时不对模型可调用 |
| `user-invocable` | 可选 | DSH 原生权限 | `false` 时不面向用户显式调用 |

### 3.4 两个主召回字段

**技能被发现和排序的主依据只有两类：**

| 依据 | 对应字段 | 要回答的问题 | 检索用途 |
|---|---|---|---|
| 使用场景提示 | `whenToUse`、`triggers` | “什么情况下应/不应使用它？” | 当前场景匹配、关键词硬命中 |
| 摘要 | `description` | “它大致是什么技法？” | 语义/词项相似度 |

正文不参与第一阶段召回，以确保大规模技能库仍轻量、快速且可解释。

### 3.5 派生数据与技能文件分离

以下内容是运行与治理产生的**派生数据**，不应频繁写回 `SKILL.md`：

- BM25 索引、分词结果、索引时间戳；
- 技能被召回、引用、确认和纠正的统计；
- 情景记忆样本；
- 未来 embedding 向量。

推荐落点：

```text
E:\Deepseek Harness\.dsh\storages\
  skill-index.json
  skill-usage-memory.json
```

这样技能正文保留可审查的知识资产，运行数据则可独立重建、清理和调参。

## 4. 工具体系

“工具”分为四种形态：

- **Agent 工具（🛠）**：模型可调用；
- **系统服务（⚙️）**：插件内部能力，不需要模型直接调用；
- **UI 能力（🖥）**：面向用户的技能库侧边栏页面；
- **提示词协议（📋）**：规范模型本轮可见内容与结构化输出。

### 4.1 技能生产与生命周期（L0）

| 工具 | 形态 | 职责 |
|---|---|---|
| `skill_create` | 🖥 / 🛠 | 用模板创建技能；强制引导填写摘要和使用场景提示 |
| `skill_edit` | 🖥 / 🛠 | 编辑结构化字段、正文和资源；触发索引失效 |
| `skill_status` | 🖥 / 🛠 | 修改 `status`，以及 DSH 原生启停策略 |
| `skill_validate` | 🖥 / 🛠 | 校验名称、frontmatter、双召回字段、重名、related 孤儿引用和状态规则 |
| `skill_distill` | 🛠 | 从会话提炼候选技能（对接 dsh-distill）；以草稿进入库，待审查 |
| `skill_export` / `skill_import` | 🖥 | 导出、备份、迁移和导入技能包 |

### 4.2 索引与检索（L1）

| 工具 | 形态 | 职责 |
|---|---|---|
| `skill_index` | ⚙️ | 扫描真源；提取结构化字段；建立和增量更新本地 BM25 索引 |
| `skill_recall` | ⚙️ | 根据当前轮 query 召回候选技能并输出可解释分数 |
| `skill_rerank` | ⚙️ | 合并硬匹配、BM25、状态规则、相关技能扩散和情景记忆，得到有序 top-K |
| `skill_search` | 🛠 | 全库兜底检索；模型主动查找冷门或未进入 top-K 的技能 |

第一期检索为本地 BM25 + 显式规则。未来可在不改变接口的前提下增加 embedding 分数。

### 4.3 每轮使用与注入（L2）

| 工具 | 形态 | 职责 |
|---|---|---|
| `skill_context_builder` | ⚙️ | 从当前用户消息和必要的最小会话主题构造本轮 query |
| `skill_inject` | ⚙️ / 📋 | 每轮运行：召回 top-K，生成本轮可见的技能卡片摘要和引用协议 |
| `skill_get` | 🛠 | 复用 DSH 现有 skill loader；按 name 加载技能正文与资源基路径 |
| `skill_search` | 🛠 | 在模型认为 top-K 不足时检索全库 |

### 4.4 引用、反馈与治理（L3）

| 工具 | 形态 | 职责 |
|---|---|---|
| `skill_citation_protocol` | 📋 | 约定 agent 回复如何结构化声明本轮实际引用的技能 |
| `skill_citation_parse` | ⚙️ | 从回复中解析并校验引用的技能名 |

## 5. 每轮运行协议

### 5.1 核心语义

技能不是会话背景知识，而是**当前轮的临时工作指引**：

- 每轮都重新判断当前场景；
- 每轮都重新召回；
- 本轮注入的技能不能作为下一轮默认继承的上下文；
- 下一轮即使主题相近，也必须重新经过召回与重排；
- 技能正文仅在模型选择使用后加载，且应被视为本轮工作材料。

### 5.2 每轮流程

```text
(1) 用户发出当前轮消息
        ↓
(2) skill_context_builder 构造本轮 query
    - 当前用户消息为主
    - 仅带入必要、压缩的工作主题，不把旧技能正文作为 query 内容
        ↓
(3) skill_recall + skill_rerank
    - triggers/name 硬匹配
    - whenToUse/description 的 BM25
    - status、related、情景记忆规则
        ↓
(4) skill_inject
    - 只注入本轮 top-K 技能卡片摘要
    - 声明“这是当前轮候选，不是永久会话上下文”
    - 声明引用输出协议
        ↓
(5) agent 选择技能
    - 命中需要执行的技法时调用 skill_get(name)
    - 可调用 skill_search 查找未进入 top-K 的技能
        ↓
(6) agent 完成工作并输出回复
    - 同时结构化声明本轮实际引用的技能
        ↓
(7) 当前轮结束
    - 技能上下文失效
    - 下一轮从 (1) 重新开始
```

### 5.3 不持久化的实现要求

实现必须满足以下结果，而不局限于特定技术手段：

1. 旧轮的技能卡片和已加载的技能正文不应在后续轮中累积为默认提示词；
2. 新轮应以新 query 独立检索；
3. 若底层 DSH 使用替换式注入，应在每轮替换先前技能注入，而非追加多个历史 catalog；
4. 若可行，优先使用每轮重建的临时/system prompt 注入；若使用 user-message 注入，也必须保证替换语义和历史不膨胀。

## 6. 召回与重排

### 6.1 输入

`skill_recall` 的输入是本轮场景 query，而不是技能正文。query 至少包含：

- 当前用户消息；
- 当前任务的必要主题摘要；
- 用户显式点名的技能名、领域词或触发词（若有）。

### 6.2 第一阶段：候选召回

1. **显式名称命中**：用户明确提到技能名，必须进入候选；
2. **触发词硬匹配**：`triggers` 与当前 query 命中，给予高优先级；
3. **场景匹配**：`whenToUse` 参与 BM25；
4. **摘要匹配**：`description` 参与 BM25；
5. **可见性过滤**：非 `active`、已禁用模型调用或 `archived` 的技能默认不进入模型候选。

### 6.3 第二阶段：重排

重排应输出每项的可解释证据，而不是黑箱分数。基础规则：

- 硬触发词命中优先；
- 使用场景提示和摘要的匹配得分加权；
- `related` 可为已命中技能带来有限扩展加成；
- 草稿、废弃、归档和禁用状态按生命周期规则处理；
- 情景记忆只在场景相似时影响排序；
- 用户明确纠正过的“场景 → 技能”错误组合应显著降权。

输出默认 top-K = 10（实现时可配置，按真实库规模和调试结果调整）。

### 6.4 兜底机制

检索式加载不能让冷门技能永远不可见：

- 模型保留 `skill_search` 全库检索工具；
- UI 有全库浏览、搜索、标签/状态筛选；
- 用户显式点名总是优先于自动召回；
- 召回调试视图可以发现漏召回并促使补充场景提示或摘要。

## 7. 引用治理与情景记忆

### 7.1 引用不是装饰，而是治理输入

agent 的最终回复必须说明：**本轮实际引用并据此工作的技能卡片是什么**。

这不是为了展示“模型知道了什么”，而是为了回答：

- 当前场景下，检索和选择对不对？
- 哪张技能被误用、漏用或需要替换？
- 技能的使用场景提示是否写得不够好？
- 重排规则是否需要被纠正？

### 7.2 引用输出协议

引用协议尚待最终定稿，但必须满足：

1. **机器可解析**：能稳定提取 skill name；
2. **用户可读**：用户能一眼看出本轮引用哪些技能；
3. **区分状态**：至少区分“已加载/查阅”和“实际用于生成建议”；
4. **可绑定反馈**：每一个引用都可被确认、否定或替换。

推荐语义（具体 Markdown/JSON/专用消息格式可后定）：

```text
本轮技能引用：
- used: positive-feedback-micro-reward
- considered: progress-visibility
```

其中：

- `used`：实际使用并影响了工作建议；
- `considered`：被召回或查阅，但未作为最终指导依据；
- 未调用技能时也应显式声明“本轮未引用技能”，避免治理系统把缺失当作解析错误。

### 7.3 用户反馈类型

用户可以针对单项引用或整个召回集提供：

| 反馈 | 语义 | 对未来的影响 |
|---|---|---|
| 确认 | 此场景用该技能正确 | 相似场景下加权 |
| 否定 | 此场景不该用该技能 | 相似场景下降权 |
| 替换 | 应使用 A，不应使用 B | A 形成正例，B 形成负例 |
| 漏召回 | 某技能应出现但未出现 | 补充正例；检查场景提示/摘要 |
| 场景补充 | 用户提供更准确场景描述 | 丰富场景指纹和未来检索 query |
| 技能质量问题 | 技能本身过宽、过窄、已过时 | 生成治理待办；由人或 agent 显式修订技能 |

### 7.4 情景记忆

情景记忆不是“把所有对话重新塞进 prompt”，而是结构化、可审查的训练样本：

```json
{
  "id": "uuid",
  "timestamp": "ISO-8601",
  "scenario": {
    "query": "当前轮原始或脱敏场景描述",
    "fingerprint": ["关键词", "领域", "任务类型"]
  },
  "retrieved": ["candidate-a", "candidate-b"],
  "cited": {
    "used": ["skill-a"],
    "considered": ["skill-b"]
  },
  "feedback": [
    { "type": "replace", "reject": "skill-a", "prefer": "skill-c" }
  ]
}
```

存储位置：`E:\Deepseek Harness\.dsh\storages\skill-usage-memory.json`。

### 7.5 反馈回灌规则

反馈以可逆、可检查的方式影响排序：

```text
相似场景 + 用户确认 skill A
  → skill A 的情景记忆加成上升

相似场景 + 用户说“不该用 A，应该用 B”
  → skill A 在该类场景降权
  → skill B 在该类场景加权

用户指出 A 的场景提示过宽/过窄
  → 建立 skill_validate / skill_edit 治理待办
  → 不自动改写 A 的正文
```

目标是使召回逐步更贴近该工作站的真实语境，同时保持每个调整可解释、可撤销、可审计。

- 搜索、标签、分类、状态筛选；
- 召回调试：输入 query，显示候选、最终排序和逐项得分证据；
- 治理视图：查看引用记录、确认/纠正统计、待处理治理问题。

### 8.2 后续写操作

- 新建、编辑、删除、归档、启停；
- 模板向导和 `skill_validate` 即时校验；
- 会话蒸馏后以草稿形式入库；
- 导入/导出、备份、版本历史；
- 聊天区直接对技能引用确认、否定或替换。

## 9. 闭环逻辑

### 9.1 使用闭环：每轮临时工作指导

```text
用户当前轮消息
  → 场景 query
  → 召回与重排 top-K
  → 本轮临时注入
  → 模型按需加载并使用技能
  → 回复 + 结构化引用
  → 本轮结束，技能上下文失效
  → 下一轮重新从场景 query 开始
```

该闭环解决“当前该用什么技法”。它不保留旧技能作为默认上下文。

### 9.2 治理闭环：越用越聪明

```text
结构化引用
  → 用户确认 / 否定 / 替换 / 标注漏召回
  → 情景记忆样本
  → 重排权重更新
  → 下一次相似场景的召回顺序改善
  → 新的引用接受治理
```

该闭环解决“系统不知道自己一开始找得对不对”的问题。

### 9.3 技能生产闭环：持续积累而不失控

```text
手写 / 蒸馏候选
  → 结构与双召回字段校验
  → 入库或草稿
  → 索引更新
  → 被召回、使用和治理
  → 修订 / 版本升级 / deprecated / archived
```

该闭环解决“技能不断增长后如何保持可用”的问题。

### 9.4 质量闭环：调试可解释性

```text
召回调试视图或用户反馈发现误召回
  → 检查 description / whenToUse / triggers / 状态 / 重排证据
  → 修正技能卡片或排序规则
  → 索引更新
  → 用相同场景回归验证
```

该闭环解决“如何把检索质量从拍脑袋变成可调、可测、可回归”的问题。

## 11. 已定决策与未决决策

### 已定

- 技能真源是 `.agents/skills/`；
- 技能是实践手册，知识库是未来独立体系；
- 技能短小、数量多、单一技法；
- 使用场景提示和摘要是召回/重排主依据；
- 每轮重新召回，技能只在本轮提示词中有效；
- 第一阶段使用本地 BM25 + 规则重排；
- agent 需要结构化输出技能引用；
- 用户反馈建立情景记忆，影响未来重排；
- 管理 UI 是独立侧边栏「技能库」页；
- 先本机 Cordis 热插拔部署，不直接修改 DSH 源码或急于发布 web-ui-all。

### 待定 / 实施中验证

1. **引用的具体编码格式**：Markdown 标记、JSON 块还是宿主专用消息类型；
2. **临时注入的具体位置**：替换式 user-message 注入，还是每轮重建 system prompt；必须满足 §5.3 的不持久化结果；
3. **场景相似度实现**：第一期关键词/规则指纹，后续是否引入向量；
4. **情景记忆的 git 策略**：作为工作站学习资产跟踪，或作为可重建运行数据忽略；
5. **未知 frontmatter 字段保留行为**：若 DSH provider 不保留扩展字段，则将其规范化置于 `metadata` 命名空间；
6. **top-K 默认值和字段权重**：以真实技能库、召回调试和用户治理反馈为依据确定。

- 新功能施工前，应确认其属于哪个层（L0–L3）和哪个闭环；

- 若实践证明某项原则不成立，应记录原因、影响范围和迁移策略，再修订本文。
